  <H3 id="s1-2" n="1.2">疊層看三個記號：路由器、本機容器、三旗標</H3>

    Claude Code、Codex、OpenRouter 的推論路由器，出廠只會走 Cursor 一條路。
    <Peek snip="router-cursor">路由器</Peek>
    <a className="xref" href="#s4">§4</a>

    <Term k="box">沙箱機器</Term>。

    <a className="xref" href="#s6">§6</a>

    <code>SAND_DISABLE_UPDATES</code>、<code>SAND_DISABLE_SENTRY</code>、{" "}

  <H3 id="s1-6" n="1.6">三種資料夾：extension、packages、shared</H3>
  <p>
    上一節把 <code>source/</code> 拆成六個行程根，這裡再往下一層看行程根裡面裝的三種東西。第一種是
    <code>host/extensions/</code> 底下的三十五個資料夾，每個都是一個功能，id
    集中宣告在一張常數表裡，三十五個 id 各對一個資料夾。
    <Peek snip="ext-ids-object">三十五個 id 一次列完</Peek>
    每個資料夾的 <code>extension.ts</code> 都輸出同一種形狀的物件：<code>id</code>、
    <code>dependencies</code>（先接好才輪到它開機的其他 extension id 清單）、
    <code>start(context)</code>（真正組裝出這個功能的地方，<code>context.deps</code>
    帶著已經啟動的那些依賴的 API）。<code>memory</code> 這個 extension 是最短的範例，三行就把
    id、依賴、start 全講完。
    <Peek snip="memory-ext-decl">最短的合約範例</Peek>
    <code>telemetry</code> 那份沒被壓成一行，讀起來更直接，一樣是同一套形狀。
    <Peek snip="telemetry-ext-decl">同一套形狀，沒壓縮</Peek>
    <code>transcript</code> 這個 extension 插進 <code>TranscriptManager</code>
    的十九個插座，細節在{" "}
    <a className="xref" href="#s3-5">§3.5</a>
    那份插座板整理過了，這裡不重複。
  </p>
  <p>
    三十五個 extension 開機的順序不是照哪張表的書寫順序排的。<code>registry.ts</code>
    裡的 <code>HOST_EXTENSION_ORDER</code> 其實只是一張完整名冊，
    <code>assembleHostExtensionRegistry</code> 拿它去檢查每個 id 是不是都有對應的實作，缺一個就丟錯。
    <Peek snip="host-ext-order">名冊不是開機序</Peek>
    真正決定順序的是 <code>resolveHostExtensionBootOrder</code>
    ：只讀每個 extension 自己宣告的 <code>dependencies</code>，對整批 extension
    做拓樸排序，算出一份誰先誰後的順序。如果某個 extension 宣告的依賴不在這個 build
    裡，或者兩個 extension 互相依賴形成迴圈，這裡會直接丟
    <code>HostExtensionGraphError</code>，不是靜默跳過、也不是照原樣硬跑下去。
    <Peek snip="ext-dep-check">缺依賴就丟錯</Peek>
    開機一節怎麼呼叫這整段見{" "}
    <a className="xref" href="#s2">§2</a>
    那份收尾流程。
  </p>
  <p>
    第二種是 <code>packages/</code>，三十一個資料夾，沒有一個有 <code>extension.ts</code>
    ，也沒有 <code>id</code>、<code>dependencies</code>、<code>start</code>
    這套生命週期合約，單純是照匯入邊界切開的函式庫：最大的 <code>packages/agent</code>
    有兩百五十六個 <code>.ts</code> 檔，<code>packages/proto</code>
    一百五十七個，<code>packages/redacted-protos</code> 八十個，<code>packages/agent-exec</code>
    六十個，<code>packages/local-exec</code> 三十七個，<code>packages/shell-exec</code>
    三十四個。行程根可以匯入 package，反過來不行：實測 <code>packages/agent</code>
    只被 <code>host</code> 匯入，共十五個檔案，<code>electron-main</code>、
    <code>node-agent-coordinator</code>、<code>shared</code> 一個都沒匯入；
    <code>packages/proto</code> 則是 <code>host</code> 六十六個、<code>electron-main</code>
    十三個、<code>shared</code> 六個。
    <Peek snip="packages-agent-import">host 匯入 packages/agent 的一行</Peek>
    反過來查 <code>packages/</code> 底下有沒有任何檔案匯入 <code>host/</code> 或{" "}
    <code>electron-main/</code>，結果是零，邊界確實是單向的。
  </p>
  <p>
    第三種是 <code>shared/</code>，裝的是知道產品長相的詞彙與基本型別：事件名稱、傳輸格式、隱私過濾規則，
    這些東西認得「這是 Grok Bot」；<code>packages/</code> 裡的函式庫則刻意不認得產品，protobuf
    編解碼、命令執行、內容遮蔽都可以換一個完全不同的產品繼續用。讀者遇到一段程式碼，先問三個問題：
    有沒有 <code>id</code>／<code>dependencies</code>／<code>start</code>
    這套生命週期合約，有就是行程根底下的一個 extension；如果是一批函式，完全不 import
    任何行程根，就是 package；如果裡面藏著事件名稱、格式、產品專屬規則，那是 shared。
  </p>
